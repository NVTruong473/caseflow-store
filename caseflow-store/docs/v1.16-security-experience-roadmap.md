# v1.16 Cross-device Experience And Password Assurance Roadmap

## Objective

Deliver an HTTPS QR transfer experience that works across desktop and phone,
plus role-aware password-change assurance, without enabling real settlement or
weakening authentication boundaries.

## Non-goals

- real bank, wallet, VietQR settlement, webhook, refund, or reconciliation;
- using an account password as a transfer PIN;
- creating an order from the experience flow;
- treating a completed experience as revenue;
- custom SMTP credentials, domain DNS, SPF, DKIM, or DMARC without buyer-owned
  infrastructure;
- enterprise MFA for admin/staff.

## Task Sequence

### SECURITY-UX-PLAN-T01 - Decisions And Execution Contract

Acceptance:

- ADR-0021 and ADR-0022 are accepted and indexed.
- The roadmap defines API, schema, UI, security, QA, migration, rollback, and
  deployment gates.
- Existing dirty work is preserved and the deployed `v1.15.0` state is
  recorded before runtime changes.

Verification:

- documentation links resolve;
- roadmap and project context agree on the active task;
- `git diff --check` passes.

### QR-XDEVICE-T02 - Domain, Schema, Repository, And APIs

Deliver:

- typed experience status/session DTOs and Zod request schemas;
- additive migration `0014_cross_device_checkout_experience.sql`;
- `checkout_experience_sessions` with RLS, constraints, indexes, updated-at
  trigger, idempotent customer/request key, and atomic completion RPC;
- token/code derivation and hashing through a required server-only secret;
- repository and use cases for create, status, complete, and cancel;
- authenticated create/cancel APIs and capability-based status/complete APIs;
- sanitized `.env.example` and migration apply/verify tooling.

Acceptance:

- the server recalculates amount from catalog data;
- duplicate client request IDs return one session;
- raw token and code are not stored;
- invalid token, amount, code, state, or expiry returns stable errors;
- five failures lock the session;
- completion is idempotent;
- no order, payment, inventory, voucher, notification, or metric changes.

Rollback:

- stop new creation first;
- keep the table while active sessions expire;
- remove routes/UI;
- drop RPC, policies, indexes, and table only after retention/export review.

### QR-XDEVICE-T03 - Desktop QR And Mobile Transfer UI

Deliver:

- replace the internal URI with the HTTPS fragment URL returned by the server;
- authenticated desktop creation, countdown, confirmation code, cancel/reset,
  open-on-this-device link, polling, expiry, completion, and errors;
- `/experience/transfer` mobile-first no-index page;
- exact amount and six-digit code form;
- pending, completed, expired, locked, cancelled, loading, offline, and retry
  states;
- bilingual copy and explicit no-real-money labels.

Acceptance:

- a second browser context with no auth cookie can open the fragment URL;
- the mobile page never sees customer PII or account password;
- successful mobile completion updates desktop without reload;
- desktop reset cancels the server session;
- QR remains square, sharp, contained, and scannable at 375px and 1440px.

### AUTH-PASS-T02 - Role-aware Password Assurance

Deliver:

- customer recovery-link request API;
- dedicated recovery-session password page;
- operations current-password plus server-secret verification;
- role-specific account UI, resend cooldown, loading/error/success states;
- server-only `OPERATIONS_PASSWORD_CHANGE_SECRET` validation;
- recovery-link delivery audit.

Acceptance:

- customer cannot use the old current-password-only endpoint;
- invalid, expired, reused, or malformed recovery links fail;
- admin/staff cannot change password without current password and operations
  secret;
- customer never sees the operations-secret field;
- admin/staff never use the customer recovery-link form;
- no credential or recovery token appears in logs, reports, screenshots, or
  client bundle.

### QUALITY-T01 - Full Verification

Required checks:

1. migration static verification and live schema verification;
2. API validation, ownership, idempotency, expiry, attempt-lock, and amount
   trust tests;
3. cross-device Playwright with separate browser contexts;
4. password role matrix and recovery-link integration tests;
5. desktop/mobile screenshots and overflow checks;
6. keyboard, focus, loading, offline, retry, and reduced-motion checks;
7. lint, TypeScript, architecture, full Playwright, build, diff check;
8. secret scan, dependency audit, security posture, and Production-safety
   checks;
9. post-test account/data cleanup and protected-role reconciliation.

No check is reported PASS unless executed.

### RELEASE-T01 - Production Migration, Deployment, And UAT

Prerequisites:

- all local gates pass;
- additive migration dry-run and rollback review pass;
- Vercel has a strong server-only experience secret;
- Vercel has the requested operations secret without exposing it;
- recovery email template uses the provider confirmation URL and redirects to
  `/account/password-reset`;
- default/custom SMTP limitation is documented honestly.

Execution:

1. apply and verify the additive Supabase migration;
2. deploy a preview and run cross-device/browser smoke;
3. deploy Production only after preview passes;
4. verify headers, routes, API envelopes, no secret exposure, no real-payment
   mutation, and mock-payment lock;
5. perform one authorized-mailbox recovery-link UAT if delivery is available;
6. rerun full Production smoke and role boundaries;
7. update architecture, handoff, known limitations, release notes, version,
   tag, push, and GitHub Release only if every release gate passes.

Blocked email delivery does not block the QR experience, but it blocks claiming
that customer password email assurance is Production-verified.
